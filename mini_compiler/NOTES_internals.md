# 从内核到 GPU 的调度地图(2026-08-14 教学笔记)

> 一句话定位:这段笔记把「内核生成之后,从入队到真正在 GPU 上执行」的全链路讲清。
> 配合 profiler + msmodeling 示例服用效果最好。

## 一、完整链路:从代码到 GPU 执行

```
你写的 model(x)
   │ ① Python 层:一个算子(x@w) / 一个 fx.Node
   ↓
② torch._C dispatcher → ATen → C++ 层
   ↓
③ _cuda_launch_kernel(把 Python 参数解包成裸指针 → 找到内核函数)
   ↓
④ cudaLaunchKernel( grid, block, args, stream )   ← 真正入队的关键
   ↓
⑤ GPU 命令队列(stream)按序消费 → 命令处理器
   ↓
⑥ 执行前检查(三件事):流的队尾空没? 资源(算/传)空没? 依赖数据(buffer)就绪没?
   ↓
⑦ GPU 内核执行:读缓冲 → 算 → 写缓冲
   ↓
⑧ 结果写进 GPU 早就准备好的缓冲 → 返回 y
```

## 二、今天反复按住的五个关键点

1. **内核 = 一串编译好的二进制指令**;它在"代码段/指令存储",不是数据区。
   - 编译出它的叫**真编译器**(inductor/TVM);我们 mini_compiler 的 `lower_c.py` 在模仿它。
2. **编译 ≠ 运行时**。
   - 编译期:把调度决策**预做完**(静态 shape 时连内存大小都能算好)。
   - 运行时:只做"分配缓冲 → 入队 → 同步 → 返回",所以看起来"少"。
   - 灵活(动态 shape / 服务 batching)才轮到运行时真正调度。
3. **申请内存是 CPU 的活,不在内核里**。
   - CPU 先分配好缓冲,再 launch 内核;GPU 只是拿地址、算、写。
   - 内核不认识"内存多大";是"输出张量的 shape+dtype"告诉 allocator 要多大。
4. **GPU 卡住的 bubble(气泡)是真实性能损失**,靠 多流/事件/重叠/调度器 填掉。
   - 这一条正好解释 msmodeling 的 `multistream_pass.py` 为什么存在。
5. **静态 vs 动态**:
   - 静态 shape → 编译期就算好需要多大,运行时照单取。
   - 动态 shape → 运行到那一步才现算现申请。

## 三、调度器到底在调什么(msmodeling multistream_pass 呼应)

一个内核"最早能开始"的时间由三把尺子取 max:

```
start = max( 流的队尾结束时间,    # stream_ready
             所需资源的占用结束,   # resource_ready(计算桶 / 通信桶)
             依赖的上游内核结束 )   # 依赖数据就绪
```

调度算法(贪心):对每个内核,试几条候选流,挑"结束得最早"的那条落位。

## 四、名词速查(都是今天出现过的)

| 名词 | 一句话 |
|---|---|
| 内核 kernel | 编译好的可执行机器指令函数(在代码段/指令存储) |
| 内核对象 | 编译好之后,可被 GPU/cpu 调用的一段机器码 |
| 入队 / launch | CPU 向 GPU 命令队列提交"执行这个内核 + 参数 + stream"的操作 |
| stream | 软件定义的排队通道(哪套命令按什么顺序);硬件(命令处理器)兑现顺序 |
| 命令处理器 | GPU 硬件:按队列/事件顺序取命令并执行 |
| 事件 event | 一个内核完成时抛的"完成信号",给别人做等待依据 |
| 依赖检查 | 内核开工前要确认:流/资源/数据 三就绪 |
| bubble 气泡 | 依赖导致 GPU 空转,调度器要压到最小的性能损失 |
| allocator / caching allocator | torch 的显存池:不每次 malloc,用完还池、下用进池(复用) |
| 静态 vs 动态 shape | 编译期就能定大小 vs 运行到那步才知道 |

## 五、和前面课程怎么接

- `lower_c.py` = 内核"出生前"的最后一道工序(图→可执行代码的语言化)
- profiler = 真实机器上"每个内核被拍出来的身份证"(算子名+耗时)
- msmodeling = 昇腾 NPU 的"性能建模",模拟每个内核跑多久 + 怎么排队调度
- 三者放一起 = 你既能"看到内核",又能"估算内核",还能"调度内核"
